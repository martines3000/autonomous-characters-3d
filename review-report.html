01 · Executive summary

The original WASM web build was removed on 2026-10-31 (commit 7f8ef75); web-related findings and logs were removed from this record. See the git history for the original text.

A compact educational boids simulation with a useful native structure, but its fast neighbor lookup changes flocking behavior and several numerical paths can corrupt simulation state.

What this repo does: Rust and Bevy display autonomous 3D cone agents that wander, flock, avoid world edges and seek a selectable target. A menu changes population and steering settings and selects naive or octree candidate lookup. The assumed load is one local interactive user, from the default 100 agents to the menu’s 50,000; the historical plot extends to 100,000.

Execution and state ownership

Each vehicle has velocity, acceleration, mass, wander angles and a Transform. Flocking reads a snapshot of all positions/velocities; each parallel task writes only its own acceleration. A second pass applies seek, or wander plus wall steering, then integration moves and rotates agents. The target selection switches every agent between seek and wander. The UI mutates one large GlobalState resource, so settings and dormant benchmark buffers are coupled.

Native work uses Bevy’s compute task pool with a fixed batch size of 64. No direct Rayon API is called.

Boundaries worth preserving

Keep rendering, input and numerical simulation separable, but start with a shared steering calculation and two candidate providers inside the existing module structure. Avoid an elaborate plugin hierarchy. A headless numerical harness would enable tests and benchmarking without loading glTF, fonts, audio or a GPU.

04 · Correctness & reliability review

Fix numerical and neighbor semantics before treating the two backends as interchangeable. Confidence describes the evidence; it is separate from impact.

F01HighConfirmedEffort: Small

Zero-vector steering poisons simulation state

Correctness / numerical safety

src/vehicle.rs:144 · src/vehicle.rs:437–481 · src/vehicle.rs:529–573 · src/vehicle.rs:291–296

Evidence
Coincident boids divide a normalized zero offset by zero. Opposing neighbors can cancel separation or alignment sums before normalize(). A boid at the selected target normalizes a zero seek vector. Cohesion calls try_normalize(f32::MIN): MIN is a large negative value, so zero is accepted and divided by zero. The fallback does not run. Acceleration *= 0 does not clear NaN.
Impact
NaNs propagate into velocity, translation and rotation. With subdivided octrees, non-finite centers/distances can also reach the closest-child unwrap in subdivision/query. A symmetric flock is a valid input, so random initial positions do not remove this risk.
Recommended improvement
Use a positive norm threshold and explicit zero-vector behavior for every steering and orientation path; skip or deterministically separate coincident pairs. Preserve the previous orientation at zero speed. Reset acceleration by assignment to zero and assert finite simulation values in debug builds.
Verification and boundaries

Exact nalgebra 0.31.4 probe: zero.try_normalize(f32::MIN) returned [NaN, NaN, NaN]; opposing velocity sums and zero separation normalization also produced NaNs. Full visual failure not run.

F02HighConfirmedEffort: Medium

Octree mode misses neighbors across leaf boundaries

Correctness / spatial queries

src/octree.rs:335–374 · src/vehicle.rs:418–455

Evidence
find_neighbors follows only the closest-center child until one leaf and returns that leaf’s points. It accepts no radius and never traverses neighboring cells. Later distance tests filter candidates but cannot restore omitted neighbors.
Impact
Changing octree capacity or enabling octree changes the flocking model. Close boids on opposite sides of any split do not separate, align or cohere. Historical speed comparisons undercount work in octree mode.
Recommended improvement
Pass the maximum active interaction radius into the query, traverse every node whose axis-aligned box intersects the query sphere, then retain the current exact per-behavior distance filters and self exclusion. Define root behavior for out-of-bounds agents before relying on box pruning.
Verification and boundaries

Actual octree.rs imported into isolated harness: capacity 1, root [−10,10]³, points (−0.01,1,1) and (+0.01,1,1). Querying the first returns only itself although the other is 0.02 units away. Use production-minimum capacity 2 with an extra distant point as a regression test.

F03HighConfirmedEffort: Medium

Steering and target controls depend on frame rate

Correctness / time integration

src/vehicle.rs:180–183 · src/vehicle.rs:281–296 · src/target.rs:90–96

Evidence
Position uses delta_seconds, but velocity adds acceleration once per rendered frame. Wander changes angles by a fixed random increment every frame, and the selected target moves two world units per frame without Time.
Impact
The same settings steer and damp differently at 30 versus 120 FPS; target movement is 60 versus 240 units/second. A rendering slowdown changes flock behavior, invalidating performance comparisons and user expectations.
Recommended improvement
Choose simulation units and a fixed simulation step (Bevy 0.9 fixed-timestep facilities), integrate acceleration with step seconds, and sample wander on simulation ticks. Scale target movement by real delta seconds; cap catch-up work. Retune existing factors because they currently encode per-frame acceleration.
Verification and boundaries

Source-level calculation: constant acceleration 1 is added 30 times at 30 FPS and 120 times at 120 FPS. The harness prints this arithmetic; this is not an end-to-end trajectory experiment.

F05MediumConfirmedEffort: Small

Cohesion loses distance before computing arrival speed

Correctness / steering

src/vehicle.rs:475–491 · src/vehicle.rs:567–583

Evidence
Both implementations normalize the vector to the neighbors’ center before computing dist = magnitude(). Every nonzero normalized displacement has magnitude approximately 1, so dist < 10 is always true and speed is reduced to roughly max_speed / 10 regardless of actual distance.
Impact
A center 1 unit away and a center 100 units away produce the same desired cohesion speed. The apparent arrival ramp is ineffective, and the incorrect calculation is duplicated.
Recommended improvement
Measure the displacement norm before normalizing; use that norm in the arrival ramp and handle zero displacement. Apply the same corrected steering calculation to both candidate providers.
Verification and boundaries

Confirmed by operation order in both source branches. Regression cases should cover 0, 1, 10 and 100 units to the neighbors’ center.

F06MediumConfirmedEffort: Small

Maximum speed is a per-axis limit

Correctness / velocity constraint

src/vehicle.rs:281–285 · src/main.rs:267–268

Evidence
simd_clamp clamps each velocity component to ±vehicle_max_speed instead of clamping vector length. The code already has a magnitude-based limit helper, but integration does not use it.
Impact
At a configured maximum of 80, velocity (80,80,80) is accepted with magnitude 138.564. Diagonal flight can exceed the advertised speed by up to √3.
Recommended improvement
Clamp velocity magnitude after integrating acceleration, with the same finite/zero safeguards as F01. Keep component clamping only if the UI explicitly intends axis limits.
Verification and boundaries

Isolated nalgebra clamp probe confirmed magnitude 138.564 for max 80. No claim that the default flock necessarily reaches this worst case.

F07MediumLikelyEffort: Small

Simulation phase order is implicit

Reliability / ECS scheduling

src/vehicle.rs:47–54 · src/main.rs:47–48 · src/target.rs:9–11

Evidence
movement and update share mutable acceleration and Transform but are added as independent systems without before/after constraints. Input, UI edits and spawning also share state across the update schedule. Access conflicts serialize incompatible systems; they do not document producer-before-consumer intent.
Impact
A schedule change can integrate yesterday’s forces before computing today’s, or add input latency. This is an ordering contract risk, not a Rust memory data race. A minimal two-system Bevy 0.9.1 probe happened to execute movement then update.
Recommended improvement
Add named system labels/sets and explicit input/config → steering → integration ordering using Bevy 0.9 APIs. Plan deferred spawn/despawn visibility deliberately; a full rewrite is unnecessary.
Verification and boundaries

Missing constraints confirmed in source; no actual order inversion observed. Add a focused schedule test checking a known force affects the intended tick.

05 · Performance & scalability review

F04HighConfirmedEffort: Medium

Coincident points cause unbounded-depth octree growth

Performance / spatial reliability

src/octree.rs:69–105 · src/octree.rs:125–128 · src/octree.rs:282–312

Evidence
Every overflowing leaf subdivides once, redistributing all points even when they share a position. There is no depth limit, minimum extent, finite-point validation or no-progress rule. Once f32 centers stop changing, subsequent points still create eight more nodes and walk the growing chain.
Impact
Clusters attracted toward a selected target are a realistic stress case. Capacity 2 and 5,000 identical points created 39,985 nodes and took about 0.961 s to build in an isolated optimized run. This can dominate a frame before parallel steering starts; larger counts worsen sharply.
Recommended improvement
Stop splitting at a depth/extent bound or when partitioning does not reduce occupancy; keep a bounded overflow bucket. Validate finite positions and define root expansion/clamping. Add clustered and coincident point stress tests before tuning capacity.
Verification and boundaries

Single-run harness timings, release on this Mac: 100 points → 785 nodes / 220 µs; 1,000 → 7,985 / 15,583 µs; 5,000 → 39,985 / 960,588 µs. These are octree-only measurements, not simulation throughput.

F10HighConfirmedEffort: Medium

Default all-pairs mode reaches billions of visits

Performance / advertised population

src/main.rs:226 · src/main.rs:263–264 · src/vehicle.rs:500–547

Evidence
Naive mode is the default. For each boid it scans the entire snapshot; the count slider permits 50,000. This is N² loop visits (N×(N−1) non-self distance computations), about 2.5 billion visits per frame at the UI maximum.
Impact
Parallelizing the outer loop cannot remove quadratic work. The stored hidden-boid benchmark already reports 243 ms/frame at 10,000 and 1.455 s at 30,000 for naive mode; current hardware was not measured.
Recommended improvement
Keep naive mode as a small-N correctness oracle. After fixing the radius query, use the spatial backend for large populations and warn/cap intentionally expensive comparisons. Profile uniform and dense distributions; a correct spatial query can still be quadratic in dense neighborhoods.
Verification and boundaries

Complexity confirmed by nested iteration; slowdown numbers are historical repository evidence, not new runtime measurements. Do not use the currently incomplete octree as a correctness-preserving default yet.

Simulation cost versus rendering cost

The octree is rebuilt serially for every flock() call, before parallel queries. A typical well-distributed tree can reduce candidate work, but its current incomplete query changes the answer. A corrected radius query costs roughly tree traversal plus candidates visited; if every boid lies within every other boid’s radius, quadratic interaction work remains unavoidable without approximation.

Additional opportunities require profiling: one new Vec of neighbor references per boid per update; new arenas/child vectors and redistribution clones per rebuild; copying full Transform values where position alone suffices; fixed batch size 64; and three separate parallel passes (flocking, extra steering, integration). None of their individual savings was measured. Reuse scratch capacity or stream query candidates only after measuring allocations; incremental tree updates are not automatically better than a compact rebuild.

Rendering instantiates a glTF scene for every agent, then propagates hierarchy/transforms, visibility and render extraction. Assets are shared through handles, which is good; shared assets alone do not establish efficient instanced drawing. The README and Slovene analysis explicitly identify rendering as a bottleneck at larger counts. No current GPU capture, draw-call measurement or CPU/GPU timing was collected, so instancing, LOD, a simpler mesh bundle and disabling unnecessary features remain experiments rather than measured remedies.

06 · Architecture & code quality review

What works well

The project stays small and readable. Components represent agent state directly. Flocking snapshots prevent in-place updates from changing neighbors partway through a parallel loop. Query filters separate vehicles and the target; Rust/ECS borrowing handles memory safety without custom unsafe code. Squared-distance tests avoid square roots for most rejected candidates. Recursive despawn cleans up scene hierarchies, and asset handles reuse the cone/font.

Small seams with a clear payoff

The octree and naive branches duplicate separation, alignment and cohesion math (src/vehicle.rs:407–493 and src/vehicle.rs:507–585). This already duplicates F01/F05. Let candidate lookup differ while one force accumulator implements the behavior. Keep a brute-force neighbor oracle independent enough to catch a spatial-query error. Use one vector representation for simple boid math if practical: Bevy’s Vec3 can remove conversion noise; removing nalgebra is an optional simplification, not a prerequisite.

GlobalState mixes tuning values, mode controls and unused sample buffers. A small simulation-settings resource and a separate measurement state would clarify change propagation, especially F08/F09. Do not generalize the public octree API beyond the actual need. Today its fields are public, create_root can leave old arenas populated, and insertion does not reject non-finite/out-of-root points. These are contract gaps if reused; current flocking builds a new tree once and does not delete points.

Wall steering subtracts velocity even when all axes are inside the world (src/vehicle.rs:206–243), which adds continuous drag; initial random velocity components are all positive (src/vehicle.rs:90–97). These are observable model choices rather than separately ranked defects without a formal behavior spec. Document them or test an intended alternative before retuning.

Top three visually impressive later features:

  1. Large, well-spaced formation morphs with later cinematic viewpoints.
  2. Emissive swarms with sampled historical ribbons and restrained bloom.
  3. Predator/prey groups in a fish/bird environment with shared animated meshes and visible avoidance.

Recommended first milestone — Showcase: 3–4 estimated sessions, Easy–Medium. Scope is exactly S1: Original default, Ocean/Dusk heading palette/background/fog/light, existing cone, no force-law changes; frame world, one auto-orbit, UI hide, correct GPU/CPU pause, simulation speed. Defer tracking, bookmarks, transitions, telemetry, new meshes and trails. Review appearance and clock changes separately within the milestone.

  • Appearance acceptance: Original reproduces current presentation; switching presets preserves count, state, target selection and physical settings; both simulation backends share the same appearance; fixed-view screenshots show readable distinct presets.
  • Control acceptance: frame-world respects current world/culling size; manual input interrupts orbit; pause freezes stepping/frame counter without reset, camera/UI remain usable, and resume preserves the flock. Speed affects simulation under an explicit paused-edit policy.
  • Performance/regression acceptance: no new per-agent appearance buffers, compute passes or normal-frame readbacks; unchanged steering inputs at normal speed. Owner-run device/frame comparisons meet a budget agreed before implementation, existing behavior checks pass, and Original/manual/speed 1.0 provides a simple rollback.

Questions requiring owner approval before dependent work:

  1. Is the primary target a polished 20k–100k interactive scene, a million-agent spectacle, or two quality modes? Which named hardware/frame budget should govern acceptance?
  2. Which theme comes first—birds, fish, drones or fireflies—and should it look stylized or realistic?
  3. Must CPU Naive/Octree support every new behavior, or may selected GPU-only features have smaller mathematical/reference fixtures? Which rendering effects may be GPU-only?
  4. For follow/formation modes, should visible spacing take priority over tight target accuracy, and what convergence/overlap tolerance is acceptable?
  5. Is obstacle avoidance soft steering, or must agents never penetrate obstacles under defined speeds/deltas?
  6. How should simulation speed/pause affect target movement, vertex animation, music and camera independently, and what should count/settings edits do while paused?
  7. Is music reaction for bundled tracks, microphone input or system audio?
  8. Should follow-density and wall-drag decisions precede behavioral presets/predators, and should the recommended milestone order change around those decisions?
